# Платформа парсеров СОЙКА

## Архитектурное правило

СОЙКА остаётся отдельной backend-программой без пользовательского интерфейса.

Пользователь работает только в Geo Analyzer. Платформа парсеров не создаёт второе окно, веб-панель, карту, форму выбора источников или отдельную вкладку. Она предоставляет внутренние Python-контракты и серверные компоненты, которые вызываются оркестратором СОЙКИ.

Административные CLI-команды и конфигурационные файлы допустимы только как инструменты эксплуатации backend-сервиса. Они не являются пользовательским интерфейсом.

## Назначение этапа

Этап создаёт платформу для будущих источников. Конкретные сайты, социальные сети, городские порталы и коммерческие API на этом этапе не включаются.

Новый источник должен подключаться отдельным адаптером без изменения классификаторов, геокодера, событий, scoring и основного оркестратора.

Платформа решает одновременно четыре задачи:

1. единый интерфейс адаптера;
2. воспроизводимый сбор с пагинацией, retry, rate limit и checkpoint;
3. обязательное досье источника и правовой gate;
4. изоляция небезопасной сетевой работы и минимизация данных.

## Fail-closed модель

Источник не запускается, пока одновременно не выполнены все условия:

- `permission_status=approved`;
- `enabled=true`;
- приложено основание разрешения или иное подтверждение правомерного доступа;
- указан reviewer и сроки повторной проверки;
- назначение анализа входит в `allowed_purposes`;
- не истёк срок review;
- доступен требуемый secret reference;
- для `public_web` получено разрешающее решение по `robots.txt`;
- источник не заявляет специальные категории, биометрию, данные детей или raw author identifiers без отдельного release-gate;
- выполнены требования сетевой allowlist и безопасного транспорта.

Отсутствие решения не трактуется как разрешение. Значение `unknown` блокирует активацию.

## Досье источника

Каждый адаптер обязан возвращать `SourcePolicy`. Политика хранит не только технические настройки, но и сведения, на основании которых было принято решение о подключении.

Обязательные разделы:

- владелец источника;
- способ доступа;
- официальная документация;
- terms of service;
- privacy policy;
- применимые юрисдикции;
- предполагаемое правовое основание;
- требуется ли отдельное разрешение;
- контакт для получения разрешения;
- ограничения авторского права и повторного использования;
- перечень персональных данных;
- план удаления и исправления данных;
- способ получения rate limit;
- список изученных документов;
- нерешённые вопросы;
- риски безопасности;
- допустимые поля и срок хранения;
- доменная allowlist;
- допустимые content types;
- версия адаптера;
- reviewer, дата review и дата следующей проверки.

Шаблон:

```text
configs/sources/source-policy-template.json
```

JSON Schema:

```text
soika_uds/parsers/schemas/source-policy-v1.schema.json
```

## Жизненный цикл источника

```text
review_required
    ↓
approved + enabled
    ↓
expired / denied / disabled
```

`review_required` является состоянием по умолчанию.

`approved` не означает бессрочное разрешение. Политика содержит `review_due_at`, а evidence может содержать `expires_at`. После истечения любого срока запуск блокируется.

`denied` используется, когда условия источника, ответ владельца, лицензия или правовая оценка не допускают сбор.

`expired` используется, когда старое разрешение или review больше нельзя считать действующим.

## Правовой подход

Платформа не заменяет юридическое заключение. Она обеспечивает техническое выполнение принятого решения и не позволяет обойти отсутствие такого решения.

Для каждого источника проверяются:

- допустимость автоматизированного доступа;
- условия API;
- условия использования сайта;
- лицензия на данные;
- договор или письменное разрешение;
- ограничения на хранение, повторное использование и публикацию;
- порядок удаления и исправления;
- персональные данные;
- трансграничная передача;
- локализация и место хранения;
- сроки retention;
- наличие специальных категорий данных;
- применимые нормы конкретной юрисдикции.

Публичная доступность комментария сама по себе не означает автоматическое разрешение на массовый сбор, хранение, объединение, повторное использование или публикацию.

`robots.txt` рассматривается как техническое ограничение crawler-доступа. Он не является лицензией, договором или средством авторизации. Положительное решение robots не отменяет terms, API rules, copyright, database rights и требования по персональным данным.

## Персональные данные и минимизация

По умолчанию:

- сохраняется только необходимый текст и минимальный набор технических полей;
- raw author identifiers не допускаются;
- author identifier либо удаляется, либо заменяется HMAC-SHA256 pseudonym;
- secret HMAC не хранится в source manifest;
- metadata проходит allowlist;
- response body не сохраняется;
- срок хранения задаётся явно;
- должна существовать процедура удаления и исправления;
- специальные категории, биометрия и данные детей блокируются отдельным release-gate;
- отсутствие данных не превращается в отсутствие проблем;
- coverage и ошибки источника сохраняются отдельно.

Хеширование author ID обычным SHA-256 без секрета не используется, поскольку оно допускает перебор известных идентификаторов. Используется HMAC с серверным secret не короче 32 байт.

## Интерфейс адаптера

```python
class ParserAdapter(Protocol):
    source_id: str
    parser_version: str

    def policy(self) -> SourcePolicy:
        ...

    def fetch_page(
        self,
        request: ParserRequest,
        checkpoint: dict[str, object] | None,
        services: ParserServices,
    ) -> ParserPage:
        ...
```

Адаптер отвечает только за:

- формирование source-specific запроса;
- получение одной страницы;
- преобразование записи источника в `SourceMessage`;
- возврат opaque JSON checkpoint;
- объявление временной или постоянной ошибки.

Адаптер не выполняет:

- классификацию;
- выделение тем;
- геокодирование;
- пространственную фильтрацию;
- поиск событий;
- scoring;
- создание отчёта;
- отображение UI;
- изменение Geo Analyzer.

## Безопасный транспорт

Адаптеру передаётся `ParserServices`. Сетевой доступ должен выполняться через `SafeHttpTransport`.

Транспорт обеспечивает:

- только `GET` и `HEAD`;
- HTTPS по умолчанию;
- доменную allowlist;
- запрет IP literal в allowlist;
- DNS resolution до запроса;
- блокировку localhost, link-local, private, reserved и multicast ranges;
- проверку каждого redirect;
- запрет redirect за пределы allowlist;
- ограничение redirect count;
- ограничение response size;
- allowlist content types;
- timeout;
- обработку `429` и `5xx` как временных ошибок;
- обработку остальных `4xx` как постоянных ошибок;
- запрет adapter-supplied `Authorization`, `Cookie`, `Host` и `Proxy-Authorization`;
- получение secrets только по `credential_reference`;
- обязательный идентифицируемый User-Agent.

Адаптеры не должны напрямую использовать `requests`, `urllib`, `socket`, shell-команды или browser automation. Исключение допускается только отдельным архитектурным и security review.

## Rate limit и retry

Rate limit задаётся в source policy и должен происходить из:

- официальной документации API;
- terms;
- договора;
- письменного разрешения;
- либо отдельного консервативного решения review.

Платформа использует token bucket.

Retry выполняется только для явно объявленных `TemporaryParserError`.

Неизвестное исключение адаптера преобразуется в постоянную ошибку. Это исключает бесконечные повторы дефектного кода.

Backoff экспоненциальный и ограничен policy.

## Checkpoint и восстановление

После каждой страницы сохраняется platform checkpoint:

- версия формата;
- opaque checkpoint адаптера;
- число страниц;
- число исходных записей;
- число выданных сообщений;
- число дублей;
- число отклонённых сообщений;
- SHA-256 ключи уже обработанных external IDs.

External IDs не сохраняются в checkpoint открытым текстом.

После перезапуска worker адаптер получает последний подтверждённый checkpoint. Уже обработанные сообщения не выдаются повторно.

Файловое хранилище является рабочей реализацией этапа. Оно атомарно записывает JSON и использует межпроцессные locks. В производственной многовузловой установке интерфейс заменяется реализацией на PostgreSQL без изменения адаптеров.

## Дедупликация

Базовая дедупликация выполняется по паре:

```text
source_id + external_id
```

В checkpoint хранится SHA-256 этой пары.

Near-duplicate detection текста не относится к платформе парсеров и выполняется на этапе preprocessing.

## Coverage и аудит

Для каждого запуска формируется `ParserCoverage`:

- статус;
- число страниц;
- число исходных записей;
- число выданных сообщений;
- число дублей;
- число отклонённых сообщений;
- предупреждения;
- ошибки;
- время начала и завершения.

Append-only audit включает:

- policy check;
- запуск;
- получение страницы;
- сохранение checkpoint;
- отклонение сообщения;
- завершение;
- ошибку.

В audit запрещено записывать credentials, raw authorization headers и полный raw response.

## Подключение нового источника

Последовательность обязательна:

1. Исследовать официальный API и разрешённые способы доступа.
2. Зафиксировать terms, privacy, robots, license и документы владельца.
3. Определить, требуется ли письменное разрешение.
4. Определить правовое основание и применимые юрисдикции.
5. Определить категории данных, retention, deletion и correction.
6. Заполнить source policy.
7. Получить legal/privacy/security review.
8. Реализовать адаптер через `ParserServices`.
9. Добавить fixture-based unit tests.
10. Добавить controlled external test без постоянной записи данных.
11. Проверить rate limit и checkpoint.
12. Активировать `approved + enabled`.
13. Настроить дату повторного review.

Нельзя сначала написать crawler, а затем искать для него правовое основание.

## Критерий завершения этапа

Этап завершён, когда:

- новый адаптер подключается через `ParserRegistry`;
- аналитическое ядро не изменяется;
- source policy обязателен;
- неутверждённый источник блокируется до network access;
- parser pages восстанавливаются из checkpoint;
- external IDs дедуплицируются между перезапусками;
- author IDs минимизируются;
- safe transport блокирует SSRF и опасные redirects;
- coverage и audit формируются;
- тесты не используют реальную сеть;
- Geo Analyzer 2 не изменяется;
- пользовательский интерфейс не добавляется.

## Нормативные и технические ориентиры

- RFC 9309, Robots Exclusion Protocol.
- Федеральный закон Российской Федерации № 152-ФЗ «О персональных данных» в актуальной редакции.
- GDPR Article 5 principles where EU personal data processing applies.
- OWASP SSRF Prevention Cheat Sheet.
- OWASP REST Security Cheat Sheet.
- NIST Privacy Framework.

Конкретное применение определяется юрисдикцией, договором и юридическим review каждого источника.
