# Оркестратор заданий СОЙКА

## Назначение

Оркестратор управляет полным жизненным циклом одного анализа СОЙКА и сохраняет состояние после каждой подтверждённой стадии. Он находится только в репозитории `soyka_geo_analisator` и не требует изменений Geo Analyzer 2.

Оркестратор не реализует бизнес-логику парсеров, геокодера, событий или риска. Эти компоненты подключаются как обработчики стадий. Граница позволяет развивать и тестировать подсистемы независимо, не передавая между ними изменяемые `DataFrame` или другие несерилизуемые объекты.

## Конечный автомат

Порядок стадий фиксирован:

1. `preparing` — проверка задания и подготовка контекста;
2. `collection` — сбор сообщений;
3. `preprocessing` — очистка, нормализация и дедупликация;
4. `nlp` — классификация и определение тем;
5. `geolocation` — извлечение и пространственная привязка;
6. `events` — события и связи;
7. `scoring` — показатели, приоритет и риск;
8. `finalizing` — сбор итогового структурированного результата.

Каждая стадия имеет checkpoint со статусом `pending`, `running`, `completed` или `failed`, номером попытки, временными метками, счётчиками обработки, предупреждениями, ошибкой и JSON-результатом.

После успешного checkpoint оркестратор больше не выполняет эту стадию повторно. При перезапуске worker выполнение продолжается с первой стадии, у которой нет состояния `completed`.

## Сохранение состояния

`FileJobStore` хранит задания как атомарно заменяемые JSON-файлы. Имя файла строится по SHA-256 от `analysis_id`, а исходный идентификатор хранится внутри документа и проверяется при чтении.

Запись выполняется через временный файл, `fsync` и `os.replace`. Для одного задания используется межпроцессный файловый lock. Каждая запись имеет монотонную `revision`; запись со старой revision отклоняется как конкурентное изменение.

Для unit-тестов и встроенного выполнения доступен `InMemoryJobStore` с тем же optimistic-lock поведением.

## Идемпотентность

При регистрации задания сохраняются:

- `analysis_id`;
- нормализованный документ `AnalysisRequestV1`;
- fingerprint семантической части запроса;
- `idempotency_key`.

Повторная доставка того же задания возвращает существующее состояние. Использование того же `analysis_id` или `idempotency_key` с другим fingerprint отклоняется как конфликт. Регистрация в файловом хранилище защищена общим lock, поэтому два worker не могут одновременно создать разные задания с одним ключом.

## Worker lease и восстановление

Перед выполнением worker получает lease с идентификатором владельца и сроком действия. Другой worker не может выполнять это задание до истечения lease.

После успешного checkpoint lease продлевается. Если процесс завершился аварийно во время стадии, checkpoint остаётся `running`, а lease — занятым до срока истечения. После истечения другой worker получает lease и повторяет только незавершённую стадию. Уже завершённые стадии не запускаются.

## Повторы

Для каждой стадии задаётся `RetryPolicy`:

- максимальное число попыток;
- начальная задержка;
- множитель exponential backoff;
- максимальная задержка.

`RetryableStageError` запускает контролируемый повтор. `PermanentStageError`, некорректный результат стадии или исчерпание попыток переводят задание в `failed` со структурированным `ContractIssue`.

Для ручного повторного запуска используется `retry_failed`. Он сбрасывает только failed-checkpoint и последующие незавершённые стадии. Результаты завершённых стадий сохраняются.

## Отмена

`request_cancel` атомарно устанавливает флаг отмены. Задание в очереди отменяется сразу. Для выполняемого задания отмена применяется после завершения текущего обработчика, перед запуском следующей стадии. Оркестратор не завершает поток принудительно и не оставляет частично записанный checkpoint.

## Формат результатов стадий

Обработчик получает `StageContext`:

- нормализованное задание;
- текущую стадию;
- номер попытки;
- идентификатор worker;
- JSON-результаты завершённых стадий.

Обработчик обязан вернуть `StageResult`. Поле `output` принимает только JSON-совместимые структуры. `DataFrame`, модели, открытые соединения, генераторы и произвольные объекты отклоняются. Большие данные позднее должны передаваться как ссылки на записи хранилища, а не как изменяемые Python-объекты.

## Материализация результата

После терминального статуса `materialize_result` объединяет структурированные выходы стадий и создаёт `AnalysisResultV1`. В метаданные добавляются:

- номер запуска задания;
- текущая revision;
- список завершённых стадий.

## Программное использование

```python
from pathlib import Path

from soika_uds import AnalysisRequestV1
from soika_uds.orchestration import (
    FileJobStore,
    PipelineStage,
    SoikaOrchestrator,
    StageResult,
)


def preparing(context):
    return StageResult(output={"territory_ready": True})


handlers = {
    PipelineStage.PREPARING: preparing,
    # Остальные обработчики подключаются соответствующими подсистемами СОЙКИ.
}

orchestrator = SoikaOrchestrator(
    FileJobStore(Path("/var/lib/soika/jobs")),
    handlers,
    worker_id="worker-cpu-01",
)

request: AnalysisRequestV1
record = orchestrator.run(request)
```

Перед `run` и `resume` проверяется наличие обработчиков всех стадий. Команды чтения, отмены и ручного retry не требуют загрузки аналитических моделей.

## CLI

```bash
soika-uds jobs --state-dir /var/lib/soika/jobs list

soika-uds jobs --state-dir /var/lib/soika/jobs status \
  --analysis-id analysis-2026-0001

soika-uds jobs --state-dir /var/lib/soika/jobs cancel \
  --analysis-id analysis-2026-0001

soika-uds jobs --state-dir /var/lib/soika/jobs retry \
  --analysis-id analysis-2026-0001
```

## Граница этапа

Этап создаёт устойчивый оркестратор и механизм восстановления. Конкретные реализации collection, preprocessing, NLP, geolocation, events и scoring подключаются следующими этапами. Geo Analyzer 2 и работающий сервис не изменяются.
