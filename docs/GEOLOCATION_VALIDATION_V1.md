# Validation set геолокации v1

Дата фиксации: 6 августа 2026 года.

## Назначение

Набор `models/geolocation_validation_v1.json` является неизменяемым qualification-набором первого production-профиля геолокации СОЙКА. Он проверяет полный путь от текста сообщения до выбранного OSM-кандидата и не используется для обучения или настройки на результатах benchmark.

## Область допуска

Профиль охватывает Москву, Санкт-Петербург и Казань. Для каждого города зафиксировано по восемь случаев, всего 24. Production approval распространяется только на уровни:

- `house`;
- `poi`;
- `landmark`.

Уровни `street`, `intersection`, `district`, `city` и `unknown` поддерживаются техническим контрактом, но не считаются подтверждёнными этим validation set. Такие результаты должны сохранять confidence и могут требовать ручной проверки.

## Происхождение данных

Тексты жалоб синтетические и не содержат персональных данных. Названия объектов, адреса и опорные координаты собраны по открытым картографическим данным OpenStreetMap с дополнительной ссылкой на поиск Wikidata для ручной сверки идентичности объекта.

Географические данные сохраняют attribution `© OpenStreetMap contributors` и условия ODbL 1.0. Синтетические тексты распространяются вместе с кодом проекта по MIT License.

Каждый случай содержит две ссылки evidence. Эти ссылки предназначены для повторной ручной проверки, а не для автоматического изменения ожидаемого результата.

## Воспроизводимость

Версия набора: `1.0.0`.

SHA-256 канонического содержимого:

`67a9573b285f0a8343f9e966fd1951b2fc1a9a3c5f36d8f72aae140b8d791685`

Digest вычисляется по JSON без поля `declared_digest`, с сортировкой ключей, UTF-8 и компактными разделителями. Loader отклоняет набор, если заявленный digest не совпадает с содержимым.

## Модельный профиль

Первичный precision-first extractor — детерминированные правила СОЙКА `rules-v2`. Natasha 1.6.0 используется как fallback и обязана пройти smoke gate. Пакет закреплён версией и SHA-256 wheel в `models/geolocation_model_audit_v1.json`.

Natasha ориентирована прежде всего на русскоязычный новостной текст, поэтому её LOC-результат не считается самостоятельным доказательством точного почтового адреса. Ограничение отражено в model audit и компенсируется explicit-address правилами, confidence и ручным validation set.

## Qualification-пороги

По умолчанию требуется:

- не менее 24 случаев и не менее 8 на город;
- extraction exact rate не ниже 0,95;
- resolution rate не ниже 0,90;
- within-tolerance rate не ниже 0,85;
- kind accuracy не ниже 0,80;
- median distance не более 300 метров;
- p95 distance не более 1 500 метров;
- доля low-confidence не выше 0,25;
- для каждого города resolution и within-tolerance не ниже 0,75.

Пороги являются частью qualification report и production registry. Их изменение требует новой версии validation set или отдельного документированного решения, нового benchmark и нового report digest.

## Сетевой режим

Qualification выполняется одним контролируемым workflow через публичный Nominatim с HTTPS, идентифицируемым User-Agent, persistent SQLite cache и ограничением один запрос в секунду. Повторный запуск с тем же validation digest восстанавливает кеш и не повторяет уже сохранённые запросы.

Публичный Nominatim не разрешён registry как production endpoint. Рабочая эксплуатация должна использовать собственный или договорной совместимый endpoint, сохраняя возможность переключения провайдера, кеширование и attribution.

## Утверждение

Данный документ является внутренней технической фиксацией validation set и критериев допуска. Он подтверждает структуру, provenance и воспроизводимость набора, но не заменяет отдельное юридическое заключение по внешним данным и инфраструктуре.
