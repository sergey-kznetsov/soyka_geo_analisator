# План разработки СОЙКА UDS Development

План рассчитан на полноценный рабочий продукт. Этапы не являются планом MVP. Каждый последующий этап опирается на завершённые и проверенные результаты предыдущего.

## 1. Аудит и нормализация исходного кода

Результат:

- полный реестр дефектов и зависимостей;
- сохранённый legacy-код;
- новый продуктовый пакет `soika_uds`;
- единые типизированные контракты;
- ленивые импорты;
- тестируемые классификаторы;
- базовый CI;
- зафиксированный порядок дальнейшей работы.

Критерий завершения: детерминированные unit-тесты проходят без сети, моделей и OSM.

## 2. Воспроизводимое серверное окружение

- выбрать и зафиксировать Python 3.11;
- заменить `pymorphy2` на `pymorphy3`;
- проверить актуальную SOIKA 0.3.0.2 и перенести полезные исправления с указанием происхождения;
- сформировать lock-файл;
- подготовить CPU и при необходимости GPU Docker-образы;
- закрепить системные библиотеки GDAL/GEOS/PROJ;
- создать команды установки моделей и проверки checksum;
- реализовать health/ready проверки.

Критерий завершения: чистая облачная машина поднимает одинаковое окружение одной командой.

## 3. Контракт Geo Analyzer ↔ СОЙКА

- утвердить версию схемы задания;
- утвердить адрес, координаты, радиус, полигон, период, источники и options;
- утвердить статусы задания;
- утвердить итоговый JSON/GeoJSON;
- обеспечить idempotency по `analysis_id`;
- определить правила отмены, повторного запуска и частичного результата;
- определить fail-open поведение Geo Analyzer.

Критерий завершения: contract-тесты обеих программ используют один набор JSON Schema.

## 4. Оркестратор полного процесса

- реализовать стадии задания как конечный автомат;
- обеспечить сохранение прогресса;
- отделить сбор, preprocessing, NLP, geolocation, events и scoring;
- добавить контролируемые повторы;
- сделать каждый этап повторяемым и идемпотентным;
- исключить передачу неструктурированных DataFrame между подсистемами.

Критерий завершения: задача восстанавливается с последнего подтверждённого этапа после перезапуска worker.

## 5. Платформа парсеров

- общий интерфейс парсера;
- реестр источников;
- единая модель `SourceMessage`;
- пагинация, rate limit, retry и checkpoint;
- дедупликация по внешним идентификаторам;
- учёт лицензий, robots, правил API и хранения данных;
- обезличивание идентификаторов авторов;
- журнал покрытия и ошибок каждого источника.

Критерий завершения: любой новый источник подключается адаптером без изменения аналитического ядра.

## 6. Парсеры приоритетных источников

Порядок конкретных источников утверждается отдельно после проверки доступности и правовых условий. Для каждого источника обязательны:

- официальный API либо разрешённый способ получения;
- тестовые фикстуры;
- обработка удаления и редактирования сообщений;
- стабильный external ID;
- временные метки и исходная ссылка;
- показатели полноты и ограничений.

Критерий завершения: каждый парсер имеет unit, integration и controlled external tests.

## 7. Preprocessing и дедупликация

- очистка HTML и служебного текста;
- нормализация Unicode;
- выделение цитат и текста автора;
- определение языка;
- нормализация времени;
- exact и near-duplicate detection;
- разделение дубля публикации и повторного обращения;
- сохранение исходного текста и трассировки преобразований.

Критерий завершения: преобразования воспроизводимы, а исходный текст никогда не теряется.

## 8. Классификация и уточнение тем

- закрепить модели по revision;
- провести аудит лицензий и обучающих данных;
- создать model registry;
- добавить batch inference;
- добавить калибровку confidence;
- определить пороги low-confidence;
- подготовить набор ручной валидации;
- измерять quality drift;
- обеспечить CPU/GPU режимы.

Критерий завершения: качество подтверждено на утверждённом наборе данных и воспроизводится на сервере.

## 9. Геолокация и OSM-контур

- разделить NER, нормализацию, поиск кандидатов и геокодирование;
- перейти на `pymorphy3`;
- исправить `NaN` fallback;
- убрать глобальную инициализацию Natasha;
- внедрить model manager;
- использовать HTTPS Overpass;
- добавить timeout, retry, rate limit и persistent cache;
- поддержать дом, улицу, перекрёсток, POI, район и ориентир;
- хранить альтернативные кандидаты и confidence;
- использовать метрическую CRS для расстояний и буферов.

Критерий завершения: адресный benchmark подтверждает точность на целевых городах.

## 10. Пространственная фильтрация территории

- фильтрация по радиусу и полигону;
- учёт пограничных объектов;
- отдельная обработка сообщений без точной геометрии;
- объяснение причины включения/исключения;
- проверка CRS на каждой операции;
- оптимизация PostGIS spatial indexes.

Критерий завершения: одинаковый вход даёт одинаковый состав релевантных сообщений независимо от порядка обработки.

## 11. События и тематическая кластеризация

- исправить хранение `message_ids` как коллекций;
- отделить embedding, dimensionality reduction и clustering;
- не переиспользовать изменяемую BERTopic-модель между независимыми объектами;
- определить минимальный объём данных;
- обрабатывать один кластер и отсутствие кластеров;
- стабилизировать random seeds;
- определить уровни building/link/road/global;
- версионировать алгоритм событий;
- сформировать объяснение состава события.

Критерий завершения: события не объединяются только по адресу и воспроизводятся на фиксированном наборе данных.

## 12. Связи, показатели и риск

- исправить пересечение идентификаторов;
- корректно преобразовывать CRS линий связей;
- утвердить формулу риска;
- разделить наблюдаемые показатели и итоговый score;
- обработать нулевой диапазон нормализации;
- обеспечить объяснимость коэффициентов;
- провести экспертную валидацию;
- версионировать веса и формулу;
- не трактовать отсутствие данных как нулевой риск.

Критерий завершения: один и тот же набор событий даёт проверяемый и объяснимый результат.

## 13. Хранилище и кеш

- PostgreSQL/PostGIS;
- миграции схемы;
- задания и статусы;
- исходные сообщения;
- очищенные тексты;
- классификация и версии моделей;
- геокодирование и кандидаты;
- события, связи и риск;
- OSM-кеш;
- политика retention и удаления;
- резервное копирование и восстановление.

Критерий завершения: повторный запуск не скачивает и не пересчитывает неизменившиеся данные.

## 14. Серверные worker и эксплуатация

- очередь заданий;
- отдельные CPU/GPU worker;
- лимиты памяти и времени;
- graceful shutdown;
- повтор после сбоя;
- отмена;
- структурированные логи;
- метрики и tracing;
- алерты;
- секреты и сетевые ограничения;
- закрытый доступ только от backend Geo Analyzer.

Критерий завершения: отказ одного задания не нарушает другие задания и основной отчёт Geo Analyzer.

## 15. Интеграция результата с Geo Analyzer

- стабильный transport между серверными программами;
- статусы выполнения;
- JSON/GeoJSON результата;
- warnings и coverage;
- совместимость версий;
- сценарий отключённого checkbox;
- сценарий ошибки СОЙКИ;
- сценарий частичного результата;
- данные для дополнительной вкладки отчёта.

Критерий завершения: интеграционный стенд формирует основной отчёт и дополнительную вкладку без ручных операций.

## 16. Полное тестирование

- unit tests;
- contract tests;
- integration tests;
- controlled external tests;
- end-to-end tests;
- regression datasets;
- geocoding benchmark;
- classifier quality tests;
- event stability tests;
- risk formula tests;
- load and soak tests;
- failure injection;
- security and dependency scanning;
- backup/restore tests.

Критерий завершения: все обязательные тестовые контуры проходят на release candidate.

## 17. Правки по результатам испытаний

- устранение выявленных дефектов;
- повторный полный regression run;
- фиксация известных ограничений;
- обновление документации и эксплуатационных инструкций;
- release checklist;
- версия и immutable container image.

Критерий завершения: нет открытых критических и высоких дефектов, а средние дефекты имеют утверждённый план и не искажают результат.

## Приоритет ближайших работ

1. Завершить нормализацию packaging, imports, contracts и CI.
2. Перейти на Python 3.11 и `pymorphy3`.
3. Переписать геокодер на разделённые компоненты и исправить сетевую работу.
4. Утвердить серверный контракт задания и результата.
5. Переписать события, связи и риск с корректной CRS и тестами.
6. После стабилизации аналитического ядра начать платформу парсеров и конкретные источники.

Парсеры не должны разрабатываться поверх нестабильного геокодера и нефиксированных контрактов: иначе ошибки сбора, NLP и пространственного анализа будут неразделимы.
