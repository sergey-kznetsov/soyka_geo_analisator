# Preprocessing и дедупликация СОЙКА

## Назначение

Подсистема `soika_uds.preprocessing` преобразует сообщения, собранные адаптерами, в воспроизводимый JSON-результат для последующих NLP, геолокации и событий. Она не изменяет исходный `SourceMessage`, не обращается к сети и не загружает модели.

Geo Analyzer 2 не участвует в preprocessing и не изменяется на этом этапе.

## Контракт сохранности

Для каждой входной записи сохраняются:

- источник и внешний идентификатор;
- исходный текст без изменений;
- исходное представление времени;
- URL, обезличенный author ID, координаты и разрешённые metadata;
- нормализованный текст;
- отдельный текст для моделей;
- выделенные цитаты;
- язык и измеренные признаки письменности;
- SHA-256 fingerprints и SimHash;
- решение по дубликату;
- полный список преобразований с SHA-256 входа и выхода каждого шага.

Даже отклонённое или исключённое из аналитического счёта сообщение остаётся в результате. Необратимое удаление исходной записи на этапе preprocessing запрещено.

## Последовательность преобразований

Алгоритм версии `1.0.0` выполняет фиксированные шаги:

1. безопасное преобразование HTML в текст без исполнения JavaScript;
2. исключение содержимого `script`, `style`, `noscript` и `template`;
3. выделение HTML `blockquote`;
4. Unicode-normalization `NFKC`;
5. удаление управляющих и zero-width символов;
6. нормализация переводов строк и пробелов;
7. удаление только точных строк из версионированного списка технических элементов;
8. выделение строк с `>` и блоков `[quote]...[/quote]`;
9. определение языка по измеряемому соотношению Cyrillic/Latin;
10. нормализация timestamp в UTC;
11. построение fingerprints;
12. детерминированная классификация дублей.

Исходный текст не используется как изменяемый рабочий буфер. Каждый шаг получает строку предыдущего шага и сохраняет hashes до и после преобразования.

## Время

Timestamp без timezone не интерпретируется как локальное время по умолчанию. Такое сообщение сохраняется, но получает решение `rejected` с причиной `PUBLISHED_AT_MISSING_TIMEZONE`.

Timezone-aware timestamp приводится к UTC. Исходное ISO-представление сохраняется отдельно.

## Язык

Встроенный детектор не является статистической языковой моделью. Он даёт детерминированный результат:

- `ru` — не менее 80% букв относятся к Cyrillic;
- `en` — не менее 80% букв относятся к Latin;
- `mixed` — присутствуют обе письменности без доминирования 80%;
- `unknown` — недостаточно буквенных признаков.

Вместе с кодом сохраняются confidence и абсолютные количества Cyrillic/Latin. Более точный versioned language model может быть подключён позднее без изменения базового контракта.

## Fingerprints

Для каждого сообщения рассчитываются:

- SHA-256 пары `source + external_id`;
- SHA-256 canonical URL;
- SHA-256 normalized text;
- SHA-256 model text;
- 64-bit SimHash модельного текста.

Canonical URL:

- приводит scheme и hostname к нижнему регистру;
- удаляет fragment;
- сортирует query parameters;
- исключает распространённые tracking parameters;
- нормализует завершающий `/` для непустого пути.

## Дедупликация

Все сообщения сначала сортируются по UTC-времени, source, external ID и text hash. Поэтому результат и представитель группы не зависят от порядка входного массива.

Проверки выполняются в порядке:

1. одинаковый source/external ID;
2. одинаковый canonical URL;
3. одинаковый model text SHA-256;
4. near-duplicate candidate через четыре 16-bit SimHash band;
5. Hamming distance;
6. token Jaccard и sequence similarity.

Пороговые значения входят в `PreprocessingConfig`, а полный config получает собственный SHA-256 digest.

## Типы решений

### `unique`

Самостоятельное сообщение. Включается в аналитический набор.

### `technical_duplicate`

Повторная доставка или публикация, которую нельзя считать новым наблюдением. Запись сохраняется, но по умолчанию исключается из аналитического счёта.

### `cross_source_repost`

Одинаковый или почти одинаковый текст опубликован другим источником. Запись сохраняется и связывается с первым представителем. По умолчанию исключается из аналитического счёта. Поведение можно изменить явным versioned config.

### `repeated_appeal`

Похожее сообщение считается отдельным наблюдением, если содержит recurrence marker либо опубликовано после настроенного минимального интервала. Оно остаётся включённым в аналитический набор и содержит ссылку на предыдущее обращение.

Эта классификация не утверждает семантическую идентичность проблем. Она фиксирует воспроизводимое техническое решение до этапов классификации и событий.

## Масштабирование near-duplicate detection

Полный попарный перебор не используется. Принятые представители индексируются по четырём 16-bit band SimHash. Подробное сравнение выполняется только для кандидатов с совпавшим band, после чего проверяются Hamming distance и текстовая similarity.

Технические дубли и исключённые репосты не становятся новыми представителями. Повторные обращения индексируются, поскольку являются самостоятельными наблюдениями.

## Интеграция с оркестратором

`PreprocessingStageHandler` подключается к `PipelineStage.PREPROCESSING` и читает завершённый output стадии `collection`.

Поддерживаются два JSON-формата collection output:

```json
{
  "messages": []
}
```

или:

```json
{
  "sources": {
    "vk": {"messages": []},
    "ok": {"messages": []}
  }
}
```

Handler возвращает:

```json
{
  "preprocessing": {
    "schema_version": "1.0.0",
    "algorithm_version": "1.0.0",
    "config_digest": "...",
    "input_digest": "...",
    "output_digest": "...",
    "stats": {},
    "messages": [],
    "analysis_message_keys": []
  }
}
```

Результат полностью JSON-compatible и сохраняется в checkpoint оркестратора. Если отдельные сообщения отклонены, стадия завершается успешно с агрегированным `ContractIssue`; ошибка одного некорректного сообщения не скрывает исходные записи.

## Границы этапа

Этап 7 не выполняет:

- лемматизацию для классификатора;
- модельное определение языка;
- semantic embedding deduplication;
- классификацию категорий и тем;
- геолокацию;
- пространственную фильтрацию;
- объединение в события;
- физическое удаление записей из хранилища.

Эти операции принадлежат последующим стадиям и должны использовать сохранённые `model_text`, duplicate decision и transformation trace.
